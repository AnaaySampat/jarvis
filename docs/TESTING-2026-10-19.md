# Test plan: the 2026-10-19 features (for Claude Code)

You are testing nine features added on 2026-10-19 to both JARVIS repositories: the phone
app (`AnaaySampat/jarvis`) and the Windows app (`AnaaySampat/jarvis-windows`). They were
built and unit-tested in a cloud session with no phone, PC or TV, so **none of them has run
on real hardware yet**. Your job is to find out what really works.

The same file is in both repos (`docs/TESTING-2026-10-19.md`). Read each repo's `CLAUDE.md`
before starting. The phone repo's rules matter during device tests, especially:
- **Never** `adb shell am force-stop com.jarvis.app`.
- Use `tauri android build`, not `tauri android dev`.

## Ground rules

- **Evidence or it didn't pass.** For every check, record what you saw: a log line, an
  `adb` output, a screenshot, or what the user reported. "Should work" is not a result.
  This is the apps' own core rule ("never claim a tool succeeded unless its return says
  so"), and it applies to this report too.
- **Ask the user for anything physical.** Examples: turning the TV fully off, putting the
  PC to sleep, leaving the home Wi-Fi, tapping a notification. Say exactly what to do,
  then wait for them.
- **Order matters.** Run section 1 (automated) first. Don't start device tests on a tree
  that fails its own tests.
- **Bugs.** When something fails, find the cause before changing code. Add a test that
  reproduces it (colocated `*.test.ts` on the phone, `test_*.py` on the desktop). Keep
  both repos in step when the same logic exists in both.
- **Docs.** Record results in the docs as you go (section 4).
- **Publishing.** Don't push tags, publish releases, or post anything publicly unless the
  user says so.

## 3. Device checks, feature by feature

Each check gives its setup, steps, the result that counts as a pass, and where to look.
Lines starting with **User:** are steps only the user can do.

### 3.1 Wake-on-LAN (TV and PC)

1. **TV MAC learned.** Send the TV any command from each app.
   - Desktop: Settings → Devices → TV should show the MAC address.
   - Phone: `localStorage.getItem("jarvis.android.tv.v1")` should contain `"mac"`.
2. **TV from deep standby.**
   - **User:** turn on Settings → Network → Remote start on the TV, then switch the TV off
     with the remote and wait about 15 minutes.
   - Confirm the TV is unreachable: `adb connect <tv-ip>:5555` from the PC should fail.
   - Say "turn on the TV" to the desktop.
   - Pass: the reply is "Turned the TV on (woke it over the network)." and the TV is on.
   - Repeat from the phone.
   - If ADB was still reachable, the normal power path ran instead. Record that, because it
     means this TV never reaches the "off" state that needs Wake-on-LAN.
3. **PC from the phone.**
   - Check the phone has the PC's adapters: `localStorage.getItem("jarvis.android.pcwake.v1")`
     should be a non-empty list. The PC sends it every time the phone connects.
   - **User:** turn on Wake on LAN in the PC's BIOS, and in Device Manager → network
     adapter → Power Management → "Allow this device to wake the computer". Then put the
     PC to sleep. The phone must be on the same Wi-Fi.
   - Say "turn on my PC" to the phone.
   - Pass: "Woke the PC — it's connected now" within about 60 seconds.
   - Failure: it should explain why, and it must not claim the PC is on.

### 3.2 Send this to the TV

1. **From the PC, YouTube.**
   - **User:** play a YouTube video in Chrome, about 10 minutes in, with that tab in front.
   - Say "send this to the TV".
   - Pass: the TV plays the same video near the same time, and the PC is paused.
   - If the reply says "from the start: it didn't take the start time", the TV's YouTube
     app ignores `&t=`. Record it; that is an unknown this test answers.
   - `[NowPlaying]` log lines appear only on errors.
2. **From the PC, Netflix.** Same steps in Chrome. Pass: the TV resumes the same title and
   episode.
3. **PC negatives.**
   - With the video tab *not* in front, it must say it can't tell which page. It must not
     send another video.
   - With Spotify playing, it must refuse.
4. **From the phone.**
   - **User:** grant JARVIS notification access, then play something in the YouTube app.
   - Say "send this to the TV".
   - Pass: the TV plays it near the same position and the phone pauses. This uses a web
     search plus YouTube's own title check to find the video ID. If it picks the wrong
     video, record the title.
5. **Share sheet.**
   - **User:** in YouTube, tap Share → JARVIS.
   - Pass: it plays on the TV.
   - Also share plain text. It should get the warning "only a YouTube or Netflix link".

### 3.3 MCP servers (desktop only; needs Node.js for `npx`)

1. Settings → MCP Servers → add:
   - Name: `files`
   - Command: `npx -y @modelcontextprotocol/server-filesystem C:\Users\<user>\Documents`
2. Pass: status shows "Connected — N tools", and the log shows `[MCP] files: N tool(s)`.
3. "Use the files server to list my Documents folder."
   - Pass: it lists the folder.
   - If the server marks that tool read-only, there should be no approval prompt. Record
     whether a prompt appeared.
4. "Use the files server to create test.txt in Documents saying hello."
   - Pass: an approval prompt appears first. Deny once (nothing created), then allow (file
     created).
5. Tick "Trusted", repeat a write, and confirm there is no prompt. Then Remove the server
   and confirm its tools are gone.

### 3.4 One memory (phone ↔ PC)

The phone must be paired with the PC and connected.

1. Phone: "remember that my favourite colour is teal".
   - Pass: within about a minute, the PC's Memory view shows it.
2. PC Memory view: Forget that fact.
   - Pass: within about a minute, it's gone from the phone's Memory → Facts too, and it
     doesn't come back.
3. Phone: make a timed routine, for example 5 minutes from now.
   - Pass: the PC's Routines tab lists it with "(on your phone)", and the PC does **not**
     run it at that time. The phone's notification does fire.
4. Desktop state lives in `<storage>\memory\sync_tombstones.json`. The phone's sync cursor
   is `localStorage` key `jarvis.android.memorysync.v1`.

### 3.5 "When I get home" (phone)

1. Phone: open the routine form, choose "When I get home", and save a routine, for example
   "turn on the TV". The voice equivalent is "when I get home, turn on the TV".
2. Home must be learned. The TV or PC has to have answered on its home address since the
   update.
   - Check: `adb shell run-as com.jarvis.app cat shared_prefs/jarvis_arrival.xml` should
     list `homes`, `routines` and `last`.
3. **Blip test.**
   - **User:** turn Wi-Fi off and on within 30 seconds.
   - Pass: no notification.
4. **Arrival test.**
   - **User:** turn Wi-Fi off for at least 20 minutes, so the 15-minute sampler records
     "away". Then turn it back on.
   - Pass: a notification "You're home: <name>". Tapping it runs the routine once. A
     second arrival the same day doesn't run it again.
   - Unknowns to report:
     - Whether the network callback fires with JARVIS fully closed (swiped away).
     - How late the sampler runs under Doze.

### 3.6 Nightly memory digest

- **Desktop.** Leave JARVIS running overnight after a day of use. Next morning check:
  - the console line `[Digest] <date>: read N message(s), learned M`
  - Memory for new facts, phrased in the user's voice
  - `<storage>\journal\<date>.md`
- **Phone.** Open JARVIS after 03:00 and check Memory → Facts. The toggle is there too.
- **Pass.**
  - The facts are true things the user said.
  - Nothing comes from what JARVIS or a web page said.
  - At most 5 facts per night.
  - Turning the digest off stops it.

### 3.7 TV by sight (phone; needs a Gemini or Vertex key)

1. With the TV on its home screen, ask "what's on my TV?". Pass: a correct description.
2. With Netflix open, ask the same. Pass: it says Netflix blocks screenshots. No guessing.
3. "On YouTube, search for lofi and play the second result."
   - Pass: the activity feed shows steps and screenshots, and it ends with "done" on the
     right video.
   - Try STOP mid-task. Pass: it stops promptly with "Stopped."
4. Report how many steps it took, and any step where it pressed the wrong buttons.

### 3.8 Replay tests and the turn recorder (desktop)

1. Run `$env:JARVIS_RECORD_TURNS = "1"; python start.py`, then have a few chat turns.
2. Pass: `%APPDATA%\Jarvis\recorded_turns.jsonl` gets one line per turn, in the shape of
   `replay_fixtures.json`.
3. If a model did something surprising, make that turn a fixture:
   - add `results`, with `feed_to_model` where the real action has it
   - add `expect`
   - run `python -m unittest test_replay`

Known finding to confirm: say "resume the TV" right after pausing it. A wrong-model reply
like "Resumed — back to Arcane." is **spoken** before the claim check runs the real
action. See `jarvis-windows/TODO.md`. Confirm whether it happens live.
